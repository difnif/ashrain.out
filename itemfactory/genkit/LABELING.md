# 라벨링 설계 — 한 번의 응답에서 최대한 여러 갈래를 걷기

## 왜 라벨이 필요한가

라벨 없이 걷은 응답은 **1비트**다(맞음/틀림). 문항에 라벨이 붙어 있으면 같은 응답 하나가
"이 학생은 〈무엇을〉 〈어떤 표상에서〉 〈몇 단계짜리 절차로〉 못 했고, 〈어떤 오개념〉을
갖고 있다"는 **6~8축의 관측**이 된다. 문항 수를 늘리는 것보다 라벨을 다는 것이 데이터를
빨리 불린다 — 같은 학생, 같은 시간, 같은 문항 수로 정보량만 몇 배가 된다.

라벨은 **출생 시점에** 붙인다. 나중에 붙이려면 문항을 다시 읽어야 하고, 그때는 이미 응답이
쌓여 있어서 소급이 안 된다. `genkit`은 실체화하면서 자동으로 붙인다(`labels.py`).

> **2026-09-07 개정** — 기존 「문항 · 유저 라벨 / 분석 알고리즘 리스트업 v2」(L-01~38 / U-01~39 /
> A-01~28)와 「문항 생성 시스템 설계 문서 v0.1」에 맞춰 다시 짰다.
> 라벨 키는 `L06_difficulty_prior` 처럼 **ID + 이름** 이라 레지스트리와 1:1로 대조된다.
> `genkit` 이 채우는 것은 **A군 L-01~11 · B군 L-13~24 · 신규 후보 L-39~49** 이고,
> C군(L-25~38, 성과 라벨)은 유저 데이터가 쌓인 뒤 `item_stats` / `item_difficulty` 쪽에서 채운다.
> **L-06(예상)과 L-25(실측)는 영구 분리** — 덮어쓰지 않는다. 둘의 차이 L-35가 생성기 성적표다.

## 6축 (위 라벨들을 읽는 관점)

| 축 | 값 | 출처 | 걷히는 신호 |
|---|---|---|---|
| ① 내용 content | `unit_id` `concept_ids` `skill` `prereq[]` | 시드 선언 | 어느 개념·선수기능에서 막히는가 |
| ② 인지 process | `process`(개념이해/절차수행/추론/문제해결/표현) `steps_n` | 시드 선언 + 자동 | 개념을 모르는가, 절차가 안 되는가, 다단계에서 무너지는가 |
| ③ 표상 repr | `representation[]`(식/수직선/좌표/표/그래프/평면도형/입체도형/글/자료) `figure_fns[]` `context` | 도형에서 자동 | 같은 개념도 표상이 바뀌면 못 하는가 (그림은 되는데 식은 안 되는 학생) |
| ④ 부하 load | `magnitude` `negative` `fraction` `decimal` | 파라미터에서 자동 | 개념이 아니라 음수·분수·큰 수가 걸림돌인가 |
| ⑤ 형식 form | `qtype` `answer_type` `choice_n` `solution_levels` | 자동 | 객관식은 되는데 서술형이 안 되는가 |
| ⑥ 진단 diagnostic | `distractor_map`(보기→오개념) `misconceptions[]` `discriminates` | 시드 선언 + 검사 | **오답이 곧 진단이 된다** |

여기에 출처·변주 정보(`seed_id` `template_id` `variant_axis` `difficulty_prior`
`time_expect` `schema_id` `source_item_ids`)가 함께 붙어, 나중에 "어느 변주축이 정답률을
얼마나 떨어뜨리는가"를 문항을 다시 읽지 않고도 집계할 수 있다.

## ⑥번이 핵심이다 — 오답↔오개념 사상

객관식 오답을 아무렇게나 만들면 "틀렸다"만 남는다. 오답 하나하나를 오개념 코드에 묶으면
학생이 ③번을 고른 순간 **"중점 대신 두 수의 합을 씀(MC-MID-01)"** 이라는 진단이 바로 나온다.
그래서 `genkit`은 **오개념 코드가 없는 오답이 하나라도 있으면 그 문항을 저장하지 않는다**(G3).

코드는 `labels.py`의 `MISCONCEPTIONS`에 등록된 것만 쓴다(자유 문자열 금지).
새 오개념은 코드를 먼저 등록하고 시드에서 코드로 참조한다 — 그래야 나중에 학생별로
`select misconception, count(*)`가 의미를 갖는다.

현재 등록된 코드는 부호·연산순서·분수·소수·절댓값·중점·거리(수와 연산), 동류항·분배·이항(문자와 식),
기울기·좌표축·정비례(함수), 넓이공식·반지름/지름·닮음비·겉넓이/부피·내각합·π(기하),
도수/상대도수·평균/중앙값·경우의 수(통계), 계산실수·단위환산·문제읽기(절차) 등 40여 개다.

## 라벨이 값을 내는 자리 — `attempts`

라벨만 붙여도 소용없다. **응답 로그가 라벨을 스냅샷으로 안고 있어야** 나중에 문항이 개정돼도
그때의 조건으로 분석할 수 있다. 제안 스키마는 `supabase/2026-09_item_gen_v2.sql` §3에 있고
(설계문서 v0.1 §8의 `attempts` 를 그대로 따르되 라벨 스냅샷과 시간 세부를 더했다), 설계 의도는 이렇다.

| 열 | 왜 |
|---|---|
| `raw_answer` | 학생이 실제로 쓴 것을 그대로 — 정답 판정 규칙이 바뀌어도 재채점할 수 있다 |
| `chosen_choice` + `misconception` | 오답을 고른 순간 진단 코드가 즉시 붙는다 (labels.distractor_map으로 사상) |
| `elapsed_ms` + `first_input_ms` | "읽고 막힌 시간"과 "쓰는 시간"을 분리 — 모르는 것과 느린 것이 갈린다 |
| `edits_n` `retry_n` | 확신 없이 고쳐가며 맞힌 것과 바로 맞힌 것을 구분 |
| `hint_level` `solution_seen` | 스스로 푼 정답과 힌트를 본 정답을 같은 값으로 세지 않는다 |
| `confidence` | 자기보고 확신도 — "확신했는데 틀림"이 가장 강한 오개념 신호다 |
| `seq` | 세트 안 순서 — 뒤로 갈수록 떨어지는 것은 능력이 아니라 피로다 |
| `labels_snapshot` | 문항 개정과 무관하게 그때의 라벨로 분석 |
| `theta_at` `b_at` | 응답 시점의 능력·난이도 스냅샷 — 모델을 바꿔도 재추정할 수 있다 |
| `distractor_tag` | **응답 시점에 박는다.** 나중에 템플릿이 바뀌면 역추적이 불가능하다 |

`elapsed_sec` 는 **기록만 하고 θ 추정에 쓰지 않는다**(설계문서 v0.1 §6 — 이탈·딴짓 노이즈가 크고
하위권일수록 편차가 심하다). 쓸 때는 중앙값 + 상하위 10 % 절단 + 표본 30 이상.

## 수집 다양성을 최대로 만드는 운영 규칙

1. **한 개념을 여러 표상으로 낸다.** 같은 중점 개념을 수직선·식·좌표로 각각 내면
   ③번 축이 살아난다. 시드의 `variant_axis`가 그 설계도다.
2. **한 개념에 객관식과 서술형을 섞는다.** ⑤번 축. 객관식만 내면 오개념은 잘 걷히지만
   표현 능력은 안 걷힌다.
3. **부하를 계단으로 만든다.** 같은 유형을 정수 → 음수 → 분수로 세 단계 두면 ④번 축이
   "개념 문제인지 수 감각 문제인지"를 가른다.
4. **오답 선택지를 재활용하지 않는다.** 오개념마다 다른 오답을 두어야 사상이 1:1이 된다.
5. **난이도는 예상값으로 두고 덮어쓰지 않는다.** 실측 난이도는 `v_item_stats`가 따로 낸다
   (PROCESS.md L-25 규약).

## 코드에서

```python
from genkit.labels import auto_labels, validate_labels, flat_tags, MISCONCEPTIONS, NEW_LABELS
lab  = auto_labels(item, tpl, seed, env, ctx)   # L-01~24 + L-39~49
errs = validate_labels(lab)                      # 통제 어휘·오개념 코드 검사 (G5가 호출)
tags = flat_tags(lab)                            # test_items.tags 용 납작한 태그 (검색·기존 앱 호환)
```

`labels` 는 `test_items.labels`(jsonb)에 통째로, `tags` 는 기존 `text[]` 에 납작하게 — 둘 다 넣는다.
앱은 지금처럼 `tags` 만 봐도 되고, 분석은 `labels` 를 본다.
